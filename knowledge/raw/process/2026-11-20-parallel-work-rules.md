# Parallel work: general rules instead of per-file fixes

> Source: Product owner direction and decision, 2026-11-20
> Collected: 2026-11-20
> Published: 2026-11-20
> Synthetic: no

After the wiki log was removed and the index and decision records were changed one by one, the product owner asked to get this right structurally, for database migrations and any other asset, "regardless of what the asset is", following how human teams collaborate, "without a lot of special treatment overhead".

Analysis (operator): the cause is shared write points. Human teams use five standard patterns:
1. No shared counters: IDs from a unique source (Rails moved migrations from sequential numbers to timestamps for this reason; issue or PR numbers come from a central allocator; or a unique name).
2. One file per item, no shared append point (changelog fragments: towncrier, changesets).
3. Aggregates are generated, not edited (documentation sites generate navigation; lockfiles are regenerated, never merged by hand).
4. Test the merged result (branch protection "up to date", merge queues).
5. Real conflicts go to the author.
The factory already had 4 (strict branch protection; the release updates the branch and reruns CI) and 5 (conflicts go back to the builder). Missing: 1 to 3.

Decision (product owner, "yes"):
- Three general rules in AGENTS.md, section "Parallel work", valid for every file: no running numbers; no shared lists edited by hand (one file per item, lists generated; on a conflict in a generated file take either side and regenerate); real conflicts merge both intents, and CI on the updated branch catches changes that merge cleanly but break each other.
- Database migrations: new files `YYYYMMDDTHHMM_name.sql` (UTC). The runner sorts by name and records applied names, so 001 to 004 stay first and unchanged. A unit test enforces the name. Known trade-off, accepted as in Rails: a migration from an older branch that merges after a newer one runs later in production than on a fresh database; CI on the updated branch tests the fresh order.
- Wiki index: generated by `npm run wiki:index` (.github/scripts/wiki-index.mjs) from front matter in every article (summary; concepts with code, status and relations). Concept map diagram and table, article tables sorted. A CI step fails when the index is stale or the front matter is incomplete or names an unknown concept.
- package-lock.json: regenerate on conflict.
- Residual: a generated, committed file can still conflict textually when two PRs change neighbouring rows, like lockfiles for human teams; the rule is to regenerate.
